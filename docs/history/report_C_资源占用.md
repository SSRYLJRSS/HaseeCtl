## 1. 测量口径说明（先讲清楚"怎么算的"）

### 1.1 主口径选择：为什么用私有提交内存，而不是工作集

**主口径 = Private Bytes（私有提交 / Commit），工作集（Working Set）只作辅助。**

原因在于工作集是**系统可以随时裁剪**的缓存，不是"真实占用"：

| 进程 | 09:30 私有 | 10:12 私有 | 私有变化 | 09:30 工作集 | 10:12 工作集 | 工作集变化 |
|---|---|---|---|---|---|---|
| HaseeCtl.App | 147.96 MB | 146.17 MB | **−1.79** | 16.21 MB | 11.22 MB | **−4.99** |
| HaseeCtl.Agent | 16.84 MB | 16.96 MB | +0.12 | 5.00 MB | 6.30 MB | +1.30 |

App 什么都没做（用户未操作），工作集就掉了 4.99 MB，而私有内存只掉了 1.79 MB。**这 3.2 MB 差值就是被系统回收的"空闲页"**——如果拿工作集比大小，会系统性地低估大进程、高估小进程，得出错误结论。

### 1.2 各指标采集方式

| 指标 | 采集方式 | 说明 |
|---|---|---|
| Private Working Set | `Win32_PerfFormattedData_PerfProc_Process.WorkingSetPrivate` + `Get-Counter "\Process(name)\Working Set - Private"` | 双源交叉 |
| 私有提交 / Private Bytes | `GetProcessMemoryInfo`（psapi.dll P/Invoke）+ WMI `PrivateBytes` | 主口径 |
| 总工作集 | `WorkingSet64` | 辅口径 |
| Virtual Size | `VirtualSize64` | .NET 保留地址空间，见 §3.3 |
| Handle / Thread Count | `Get-Process` 对象属性 | — |
| CPU 累计时间 | `TotalProcessorTime` | 绝对累计值，非瞬时% |
| IO 读/写累计字节 | `ReadTransferCount` / `WriteTransferCount` | 累计值 |
| GDI / USER 对象 | `GetGuiResources`（user32.dll P/Invoke） | 见 §1.3 权限说明 |

### 1.3 关于"不可读（权限）"的诚实标注

**`DCHUService.exe`（PID 5484）是 SYSTEM 账户的服务进程，非管理员调用 `OpenProcess` 返回 `err=5 ACCESS_DENIED`。**

因此该进程的 **GDI / USER 对象数记为「不可读（权限）」，不是 0**。它的内存字段仍可通过 `Get-Process` / CIM 读到，所以内存部分数据完整。

同时，早期一次采样中 `DCHUService` 的 WorkingSet 读到 0 —— 经 6 次间隔 600 ms 的稳定复测确认，那是**采样瞬时假象**。稳定值为 4.20 MB，本报告全部采用稳定值，**未用 PeakWorkingSet 冒充 Current**。

### 3.3 必须解释的现象：App 私有 146.65 MB 而工作集仅 26.65 MB

这是用户特别要求解释的点，且**绝不能**拿来和 FnKey 的 57.02 MB 直接比大小。

**现象数据：**

| 指标 | HaseeCtl.App | FnKey.exe | 比值 |
|---|---|---|---|
| 私有提交 | 146.65 MB | 57.02 MB | 2.57× |
| 总工作集 | 26.65 MB | 5.07 MB | 5.26× |
| **私有工作集** | **15.06 MB** | **2.11 MB** | 7.14× |
| PeakWorkingSet | 217.05 MB | 87.17 MB | 2.49× |

**这是什么：.NET / WPF 的"预留未触及"（reserved-but-not-committed-touched）**

1. **.NET 运行时启动时会向操作系统申请一块很大的虚拟地址空间**（从 Virtual Size 2.27 TB 可见，这是 GC 的保留区）。`Virtual Size` 2.27 TB 不是占用，只是**地址空间的预约**——64 位进程地址空间有 128 TB，预约不等于使用。

2. **私有提交（Private Bytes）= 已向系统"记账"但未必已载入物理内存的页**。当 WPF 加载 UI 框架、编译 XAML、初始化渲染管线时，会一次性 `VirtualAlloc` 提交一大块内存。这些页**只要没被真正读写，就没有对应的物理页**，因此不计入工作集。

3. **工作集（Working Set）= 此刻真正映射在物理 RAM 上的页**。App 只有 26.65 MB 在工作集里，说明 **146.65 − 26.65 = 120 MB 是"已提交但尚未触及"的储备**。

4. **私有工作集（Private Working Set）= 工作集中不与其他进程共享的部分**，App 仅 15.06 MB——这是它真正独占的物理内存。

**对用户的实际影响——分三层看：**

| 层面 | 影响 | 严重度 |
|---|---|---|
| **物理内存** | 只占 26.65 MB 工作集（含共享页），占 32 GB 的 **0.08%**。未触及的 120 MB 不消耗物理 RAM。 | 无影响 |
| **提交额度（Commit）** | 确实占用 146.65 MB 提交额度。本机 Commit Limit = 55.09 GB，已提交 19.61 GB，**剩余 35.43 GB**。146 MB 只占剩余额度的 **0.4%**。 | 无影响 |
| **页面文件** | 只有在物理内存紧张、系统需要换页时，这 120 MB 才可能被换出到 pagefile。本机可用物理内存 **23.84 GB**，**不会触发换页**。 | 无影响 |

**为什么不能直接和 FnKey 比大小：**

- FnKey 是**原生 Win32 程序**，没有托管堆、没有 JIT、没有 WPF 渲染管线。它的 57.02 MB 私有内存基本是"实打实的"数据。
- HaseeCtl.App 的 146.65 MB 里，约 **120 MB 是 .NET/WPF 框架的储备池**，属于"预支但未花"。
- **公平的比法是看工作集**：App 26.65 MB vs FnKey 5.07 MB，App 确实更大（WPF 本身就要 20+ MB 基线），但**绝对量在 32 GB 机器上完全无感**。
- 真正该关注的是**增长趋势**。见 §5：App 私有内存 30 分钟仅 +0.488 MB，slope +0.008 MB/min，**无泄漏**。

> **一句话结论**：146.65 MB 这个数字看着吓人，但它 82% 是"预订了但没住的房间"。实际住的只有 26.65 MB（工作集）/ 15.06 MB（独占），在 32 GB 内存上属于零感知。**正确结论是「App 打开时内存开销可忽略」，而不是「App 比 FnKey 大三倍所以更差」。**

### 3.4 App 打开 vs 关闭的真实代价

Lead 已确认采用 A 口径（**不关闭用户窗口**，基于源码证据：`MainWindow.xaml` 无 Closing 拦截、`App.xaml.cs:112-116` 退出即 Dispose、Agent 与 App 为独立进程、`TrayApp.cs:76-81` App 关闭后 OSD 静默返回）。

因此"App 关闭后"的数据由 **Agent 单进程实测值**直接给出，无需真的关窗口：

| 状态 | 私有提交 | 工作集 | 相对常驻态的增量 |
|---|---|---|---|
| Agent 单独常驻（托盘，开机自启） | 17.49 MB | 7.06 MB | — |
| Agent + App（用户打开界面） | 164.14 MB | 33.71 MB | **+146.65 MB / +26.65 MB** |

**即：打开界面的代价 = 146.65 MB 提交 / 26.65 MB 物理内存。** 关掉界面这个开销就完全消失。由于用户是"偶尔看风扇曲线"而非"常开"，**日常有效占用应按 17.49 MB 计**。

### 5.4 ★句柄与线程：存在真实的周期性增长★

这是本次测量**最重要的发现**，需要单独讲清楚，因为简单的线性回归会得出**完全错误**的结论。

#### 5.4.1 先说错误结论长什么样

如果对全部 59 个采样点直接做线性回归：

#### 5.4.7 那次 −444 是什么？——GC finalizer 批量回收，不是线程池 trim

一开始，我误判这是线程池 worker 空闲超时（`ThreadTimeoutMs`）导致的 trim。**这个解释被数据否定了**，以下两条证据足以排除它。

**证据一：句柄掉 444 个，工作集反而暴涨 9.2 MB。**

| 指标 | 09:49:07 | 09:49:38 | 变化 |
|---|---:|---:|---:|
| 句柄 | **913** | **469** | **−444** |
| 工作集 (Working Set) | 5.27 MB | **14.47 MB** | **+9.20 MB** |
| 私有内存 (Private) | 16.95 MB | 17.61 MB | +0.66 MB |
| 私有工作集 (Private WS) | 2.45 MB | **6.31 MB** | +3.86 MB |

线程池 trim 是"worker 线程空闲后自行 exit"，是一个**轻量操作**，绝不会让工作集暴涨 9 MB。而"工作集 + 私有工作集同时暴涨"是 **GC 在遍历托管堆**的典型指纹——遍历时要逐页触碰对象头和同步块，把大量冷页拉进工作集。这是 GC 的代价，也正是 GC 的铁证。

**证据二：11 分钟内零回落。**

在 `_verify/trim_cpu_corr.csv` 中，10:07:23 → 10:18:11 连续 **39 个采样点（11 分钟）**，句柄从 679 **单调涨到 811，一次回落都没有**，期间 CPU 在 0.0%–33.8% 之间剧烈波动。若回收真是按 `ThreadTimeoutMs`（十几秒量级）在检查，绝不可能 11 分钟不触发一次。

**正确机制：**

> `Thread` 对象本身是 GC 管理的托管对象。线程池 worker 退出后，其 `Thread` 对象仍留在堆上并被句柄表引用；只有当 **GC 判定该 `Thread` 对象死亡并执行 finalizer** 时，其 OS Thread 句柄与配对 `Event` 才被释放。GC 是**积累到某一代或内存压力阈值才触发**的，因此表现为"长时间线性累积（913 这个峰值用了约 19 分钟）→ 一次性批量释放 444 个 → 重新累积"的锯齿。这次 GC 同时把工作集从 5.27 MB 抬到 14.47 MB，是遍历堆的副作用。

| 观测事实 | 说明 |
|---|---|
| PID 24464 **从 08:42:03 到 10:00 从未改变** | 不是进程重启导致的清零 |
| 无 HaseeCtl 计划任务 | 不是外部定时器 |
| 清零后线程数仍为 15，未变 | 线程对象被回收但线程池保持容量 |
| 清零后立刻恢复线性增长 | 新一轮累积周期开始 |
| 线程状态全部为 `Wait`，其中 6 个 `EventPairLow` | 线程池空闲 worker |
| **同期工作集 +9.20 MB、私有工作集 +3.86 MB** | **GC 遍历堆的指纹** |
| **11 分钟内零回落（39 个采样点）** | **排除 `ThreadTimeoutMs` 定时检查** |

**回收周期不做定量结论。** 观察到至少一次主动回收（09:49:38，句柄 913→469），机制为 GC finalizer 批量回收；回收周期未获多次样本验证（n=1），且其本质由 GC 触发而非定时器，取决于分配速率与内存压力，**故不对周期给出数值**。

#### 5.4.8 这个缺陷的严重性评估

| 维度 | 评估 |
|---|---|
| **会不会耗尽系统资源** | **不会**。系统句柄表实测 4.39 MB、动态扩容、注册表未设 `MaxHandleCount`/`ObjectLimit`（无固定上限）；当前峰值 913，占系统总量 182,861 的 0.5%。 |
| **会不会内存泄漏** | **不会**。私有内存在回收后只抬升 0.66 MB 然后稳定，`analyze_soak.py` 判定 slope +0.030 MB/min、涨跌比 14:11、无单调性。 |
| **会不会 CPU 异常** | **不会**。CPU 增量恒定为 +0.015 s/周期（即 0.05% 占空比），且与负载无关（CPU 3.5%–33.8% 波动时句柄增速恒定 +6/30 s）。 |
| **实际危害** | **低，但是真实缺陷**。当前实测挡板是：**Agent 提交量稳定在 17.53–17.61 MB，未随残留 Thread 对象增长而上涨，说明线程栈页未被触及（未提交），现在无害**。真正的问题是**设计缺陷**——`Task.Run` 发起后没有任何等待或取消机制（`_maintenanceBusy` 只防并发，不防累积），把释放时机整体押在 GC 上。 |
| **最坏情况（理论上限，非预期）** | 若 GC 长期不触发（实测已观测到最长 29 分钟未触发；若极端负载下 GC 延迟数小时），约 17,280 个残留 Thread 对象 × 每线程默认保留 1.5 MB 栈 ≈ **25 GB 虚拟地址**。64 位地址空间（128 TB）充裕，**但栈页若被逐步触及会转化为真实提交量/物理内存上涨**——这才是长期风险的真实形态，比"句柄耗尽"现实得多。实测当前未发生。 |
| **建议** | ① 改用 `System.Threading.Timer` 或 `async/await` + `Task.Delay` 长驻循环替代每周期裸 `Task.Run`；② 或把维护任务放入**长驻单线程 + 手动节流**，而不是每周期新建 Task；③ 若保留现状，至少给 `Task.Run` 返回值做异常观察，避免吞掉未处理异常。 |

### 7.3 结论：**可以长期稳定运行** ✅

**量化依据：**

1. **内存占用占比 0.054%（日常）/ 0.504%（开界面）**，在 32 GB 机器上完全无感。即使按最悲观的 24h 线性外推也只有 60.5 MB（0.19%）。
2. **无内存泄漏**：私有内存 30 分钟涨跌比 14:11，R²=0.68，无单调性。GDI/USER 对象零增长。
3. **无换页压力**：`Pages/sec = 0.00`，页面文件仅用 28.9%，可用物理内存 75%。
4. **CPU 占用 0.0229%**，比旧方案 FnKey 的 0.1258% 还低 5.5 倍。
5. **零磁盘 IO**（静置态），不磨损 SSD、不打扰机械硬盘。
6. **唯一需要关注的项是句柄周期性增长（+12/min）**，但它由 .NET GC finalizer 批量回收（实测一次释放 444 个），峰值 913，占系统句柄总量 182,861 的 0.5%；系统句柄表 4.39 MB、动态扩容、无固定上限，**不构成稳定性威胁**。当前提交量稳定 17.53–17.61 MB，未随残留 Thread 对象增长而上涨，说明栈页未被触及，现在无害。

**但建议修复**：`TrayApp.RunMaintenance()` 每 30 秒裸 `Task.Run` 无回收路径，是设计缺陷。虽然当前 .NET GC finalizer 会批量兜底回收，但**把释放时机整体押在 GC 上不是可以依赖的保证**——GC 触发时机取决于分配速率与内存压力，在极端负载下可能长时间不触发（实测已观测到最长 29 分钟未触发）。修复成本很低（改用 `System.Threading.Timer` 周期性回调，或 `async` 循环 + `Task.Delay` 长驻任务），建议纳入下一版。

### 7.5 卸载官方 CC 之后的实际常驻 footprint（重要：分两种口径）

**这一节最容易出错，因为它取决于卸载 CC 应用后驱动层服务是否还活着。**

很多人假设"卸载 CC = 官方 related 进程全部消失"。**这个假设是错的**，必须区分：

| 进程 | 来源 | 卸载 CC 应用后是否仍在 |
|---|---|---|
| `HaseeCtl.Agent` | 开源重写，`%LOCALAPPDATA%\Programs\HaseeCtl` | ✅ 当然在（**17.49 MB**） |
| `DCHUService.exe` | **`CCDCHUService`，属于 oem154 驱动包的服务** | ⚠️ **仍在**。CCDCHUService 随**驱动包**安装、不随应用卸载；且清理脚本里 `sc detele` 拼写错误（正确是 `sc delete`），导致该服务从未被删除——**19.0 MB** |
| `FnKey.exe` | UWP FullTrust 应用，由 CC 目录下的 `LaunchFnkey.exe` / `CClnk.exe` 拉起 | ❓ **大概率不再被拉起**（见下方判断依据） |

#### 判断依据：FnKey 的父进程与启动时机

| 证据项 | 实测值 | 含义 |
|---|---|---|
| **FnKey.exe 父进程** | **`explorer.exe` (PID 1724)** | 由用户会话内的启动器拉起，不是服务直接 fork |
| FnKey 启动时间 | **08:39:39** | — |
| 系统启动时间 | **08:06:08** | — |
| 两者差值 | **晚 33 分钟** | **不是开机自启**（真正的开机自启会与系统启动同时或由服务在秒级拉起） |
| 包清单 StartupTask | **无** | 不存在 UWP 开机启动声明 |
| 注册表 StartupTask 子键 | **无** | 不存在注册表启动项 |
| 计划任务 | **无相关项** | 不是定时拉起 |

→ **结论：FnKey 是被 CC 安装目录下的 `LaunchFnkey.exe` / `CClnk.exe` 在用户会话建立后（登录约 33 分钟后）拉起的。这两个 exe 都在 `C:\Program Files (x86)\ControlCenter`，卸载 CC 后目录消失，FnKey 大概率不再被拉起。**

#### 两种口径的常驻 footprint

| 口径 | 组成 | **常驻总计** |
|---|---|---:|
| **保守态**（只卸载 CC 应用，不动驱动层） | Agent 17.5 + DCHUService 19.0 | **≈ 36.5 MB** |
| **乐观态**（另按清理清单手动 `sc delete CCDCHUService`） | 仅 Agent | **≈ 17.5 MB** |

> **旁注：若 FnKey 意外仍被拉起**（例如 `LaunchFnkey.exe` 被复制到其它路径、或有未知启动源），常驻会回到 Agent 17.5 + DCHUService 19.0 + FnKey 57.0 = **≈ 93.5 MB**。相对于 32 GB 内存（占 0.29%）依然无压力，但会在任务管理器里看到多一个官方进程。

**对比总账：**

| 状态 | 常驻内存 | 占 32 GB |
|---|---:|---:|
| 装 CC 时期（当前实测） | 75.99 MB | 0.233% |
| **卸载 CC 后 · 保守态** | **36.5 MB** | **0.112%** |
| **卸载 CC 后 · 乐观态** | **17.5 MB** | **0.054%** |
| 卸载 CC 后 · FnKey 意外存活 | 93.5 MB | 0.287% |

**报数纪律：不应只报 17.5 MB。** 17.5 MB 是"驱动层也被彻底清理"的乐观态；**用户若只做标准的"卸载应用"操作、不动 `CCDCHUService`，真实常驻是 36.5 MB**。两者都在安全范围内，但口径必须交代清楚，否则用户装了之后发现任务管理器多一个 `DCHUService.exe` 会认为报告失实。
