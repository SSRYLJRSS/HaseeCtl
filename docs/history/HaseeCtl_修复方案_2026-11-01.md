## 二、F1：充电上限关闭态不下发（P0-7，最高优先级）

### 现状

`src/HaseeCtl.Core/Apply/Engine.cs:157`

```csharp
if (Settings.Charge.Enabled) ok &= Step("充电上限", ApplyCharge);
```

### 为什么是 bug

`ApplyAll()` 在**开机、唤醒、用户点「重新应用」**时被调用。这行 `if` 导致：当充电上限为**关闭**状态时，`ApplyCharge()` 根本不被调用 → EC 里残留的限充设置**永远不会被纠正**。

场景：你之前设过 70/80 限充，之后关掉开关。如果关的那一刻 EC 写入失败，或者你换了电池/重置了 EC，那么此后每次开机都不会下发"关闭"指令，电池会一直卡在 70% 充不满，而界面上开关明明显示"关"。

### 改法

```csharp
// 改前（Engine.cs:157）
if (Settings.Charge.Enabled) ok &= Step("充电上限", ApplyCharge);

// 改后
ok &= Step("充电上限", ApplyCharge);
```

### 为什么不会引入新问题（已逐项核实）

1. **`ApplyCharge()` 本身已经完整支持两种状态**。`Engine.cs:223-230`：
   ```csharp
   /// <summary>Send the saved charge window, including "disabled" (status 0).</summary>
   public void ApplyCharge()
   {
       using var _ = _hw.Enter();
       if (Charge is null) return;
       var c = Settings.Charge;
       Charge.Set(c.Enabled, c.Start, c.Stop);
       Log.Write(c.Enabled ? $"应用充电上限 {c.Start}%/{c.Stop}%" : "已关闭充电上限");
   }
   ```
   XML 注释原文就写着 "including **disabled (status 0)**" —— 作者本来就设计成两态都能发。

2. **幂等，可以重复下发**。`ChargeService.cs:27-29`：
   ```csharp
   /// <summary>status 0 disables the limit; 1 enables with the given window.</summary>
   public void Set(bool enabled, int start, int stop) =>
       dchu.Ex4(31, (byte)(enabled ? 1 : 0), (byte)start, (byte)stop);
   ```
   连续发两次 `Ex4(31, 0, 70, 80)` 与发一次效果相同（都是"关闭限充"）。

3. **未连接驱动时不会受影响**。`ApplyCharge()` 第二行 `if (Charge is null) return;`。
   `Charge` 声明为 `public ChargeService? Charge { get; private set; }`（`Engine.cs:37`），在 `Connect()` 里 `Charge = new ChargeService(dchu);`（`Engine.cs:69`）**无条件创建，不做能力探测**。所以为 null 只发生在**尚未 Connect 成功**时。
   而 `ApplyAll()` 第一行就是 `if (!EnsureConnected()) return false;`（`Engine.cs:151`），执行到 `ApplyCharge` 时 `Charge` 必然非空。

   > ⚠️ **修正（自检第 28 轮）**：本文档早期草稿写作"根据能力探测赋值，不支持的机型为 null"，**这是错的**。`ChargeService` 无条件创建。真正保护不支持机型的是 `Ex4(31, ...)` 在 EC 侧被忽略（`Dchu.Ex4` 的返回不检查），而 `Try`/`Step` 会吞掉异常。**结论不变：不改坏任何东西；但不要指望代码层面主动跳过。**

4. **`SetChargeLimit()` 已经在无条件调用 `ApplyCharge()`**（`Engine.cs:301-312`），说明"关闭态下发关闭指令"这条路径**本来就存在并且在用**，只是 `ApplyAll` 漏了。本改动是让两条路径一致，不是新增行为。

5. **`Step()` 自带异常隔离**（`Engine.cs:162-168`），`Ex4` 抛异常只会让这一步返回 false，不影响后面的键盘灯/系统设置。

### 代价

每次 `ApplyAll()` 多一次 EC 写入（`Ex4(31,...)`）。`ApplyAll` 只在开机/唤醒/手动"重新应用"时跑，频率极低，可忽略。

### 验证方法

1. 编译 → 跑 `dotnet test`（`EngineTests` 应全绿）
2. 手动：关闭充电上限 → 重启 → 看日志是否出现 `已关闭充电上限`
3. 手动：开启 70/80 → 重启 → 日志出现 `应用充电上限 70%/80%`

## 三、F2：显卡切换非原子（P0-6）

### 现状

`src/HaseeCtl.App/Pages/GpuPage.xaml.cs:79-80`

```csharp
_state.Update(s => s.Gpu.Mode = (int)m);              // ① 先写配置文件
_state.Engine.WithHardware(() => _state.Engine.Gpu?.Switch(m));  // ② 再切 EC
```

### 为什么是 bug

`Engine.UpdateSettings`（`Engine.cs:126-143`）在 `mutate` 之后**立刻 `SettingsStore.Save`**：

```csharp
mutate(_settings);
SettingsStore.Normalize(_settings);
if (SettingsStore.Save(_settings) is { } stamp) _stamp = stamp;
```

所以 ① 一旦执行，配置就已经落盘。如果 ② 抛异常（`Ex4(22, mode)` 失败），`catch` 只会弹个框，**配置文件里已经写着新模式了**。下次开机 `ApplyAll` 会拿这个错误的值去下发，而界面重启后会显示"当前模式 = 新模式"，与实际 EC 状态不一致。

### 改法（只对调两行）

```csharp
// 改后
_state.Engine.WithHardware(() => _state.Engine.Gpu?.Switch(m));  // 先切 EC
_state.Update(s => s.Gpu.Mode = (int)m);                          // 切换成功才落盘
```

### 为什么不会引入新问题（已逐项核实）

1. **`Switch` 不读配置**。`GpuService.cs:29`：`public void Switch(GpuMode mode) => dchu.Ex4(22, (byte)mode);` —— 它只吃参数 `m`，与 `Settings.Gpu.Mode` 无关。所以先调用它不需要配置先就位。

2. **`_state.Update` 不参与切换决策**。`UiState.cs:71`：`public void Update(Action<AppSettings> mutate) => Engine.UpdateSettings(mutate);` —— 纯持久化，没有副作用。

3. **反过来还更安全**。原顺序下如果 `Update` 自己失败（磁盘满/权限），会直接跳到 `catch`，EC 完全没动；新顺序下先切 EC 再写盘。

4. **`_current` 判断逻辑不受影响**。`Apply()` 开头的 `if (_current is not null && mode == _current.Current)` 用的是 `_current`（从硬件读回的状态），不是配置，本次不改。

### 必须说清的局限

**局限 1：`Switch()` 无返回值、无读回。**

`GpuService.cs:29`：`public void Switch(GpuMode mode) => dchu.Ex4(22, (byte)mode);`

所以"切 EC 是否真的成功"这个程序**无法判断**。本改动只能保证"**抛异常时不落盘**"。若 EC 静默失败（不抛异常但不生效），配置依然会写入。

**要彻底解决需要 `Ex4(22,...)` 读回校验，但那属于改动 `GpuService` + 理解厂商返回码，不属于"最小修改"，本方案不做。**

**局限 2：`shutdown.exe` 启动失败时仍会误报"切换失败"（改前改后一样）。**

`try` 块（`GpuPage.xaml.cs:76-88`）把 `Update`、`WithHardware(Switch)`、`Process.Start(shutdown.exe)` 全包在里面。如果前两步都成功、只有重启失败，会跳到 `catch` 弹"切换失败"——而此时 EC 已切、配置已写。

> **这不是本改动引入的**：原顺序下同样都是"EC 已切 + 配置已写 + 弹失败框"。
> 修它需要把 `Process.Start` 挪出 `try`，属于额外改动，不在本方案范围内。

### 验证方法

1. 编译通过
2. 手动：选一个不同模式 → 确认框点"否" → 配置不变（原有行为）
3. 手动：断电/拔 EC 场景难造，主要靠代码审查确认顺序

## 四、F3：飞行模式假成功（P0-4）—— 只修失败路径

> **⚠️ 本节已按 HaseeCtl 实测结果重写。** 方案初版的 F3 是"成功后读回 `AirplaneOn()`"，**那个方案已被证伪并废弃**，原因见 §4.1。现在施工的版本只改失败路径。

### 4.1 为什么废弃了"读回"方案（实测证据）

初版想法：调完 DLL 后 `bool now = AirplaneOn(); return now;`，用读回值反映真实状态。

**这个想法在这台机器上必然错**，因为 `AirplaneOn()` 读的 `RadioKey` 根本不会被本程序或那个 DLL 改写：

| 验证项 | 实测结果 |
|---|---|
| `RadioKey` 当前值 | `reg query` → `0x0`（REG_DWORD） |
| `InsydeAirplanemodehid.dll` 里有没有 `SystemRadioState` 字符串 | **没有**（只有 `SetAirplaneMode` 导出名） |
| 全仓库 `grep "RadioKey\|SystemRadioState"` | **只 2 处**：`SystemService.cs:15` 定义、`:77` 唯一读取点。**从无写入** |
| 谁在维护这个键 | Windows 的 `WlanRadioManager.dll` / `WwanRadioManager.dll` / `XboxGipRadioManager.dll`（`HKLM\...\RadioManagement\{GUID}\` 下注册的 Radio Manager） |

结论：`SetWmi(121,26)` 和 `SetAirplaneMode()` 都**不碰**这个注册表键。读回值永远等于调用前的值。**若照初版施工，会出现"明明切成功了，OSD 却报关闭"的新 bug —— 这比原来的 bug 更糟。**

### 4.2 现状

`src/HaseeCtl.Core/Features/SystemService.cs:82-90`

```csharp
public bool ToggleAirplane()
{
    bool target = !AirplaneOn();
    Try(() => dchu.SetWmi(121, 26, (uint)(target ? 1 : 0)));
    try { SetAirplaneMode(target ? 1 : 0); }
    catch (Exception ex) { Log.Write("InsydeAirplanemodehid 调用失败: " + ex.Message); }
    Log.Write("飞行模式 -> " + (target ? "开" : "关"));
    return target;   // ← 无论 DLL 成败都返回 target
}
```

两个问题：

**P0-4（假成功）**：`SetAirplaneMode` 抛异常时只写日志，仍 `return target`。调用方 `TrayApp.cs:357` 拿到 `true` 就弹"飞行模式已开启"。

**P0-3（读写不同源）**：见 §4.1 —— 读的是 `SystemRadioState`，写的是 EC 位 + DLL，两者不同源。这个**不改**（原因见 §4.5）。

### 4.3 实际施工的改动（已提交）

只加 3 行有效代码 + 5 行说明注释，**成功路径一个字没动**：

```diff
     bool target = !AirplaneOn();
     Try(() => dchu.SetWmi(121, 26, (uint)(target ? 1 : 0)));
+    // DLL 抛异常说明这一次切换没做成，返回切换前的状态（即 !target），
+    // 让调用方显示的 OSD/文字是真实状态而不是谎报成功。
+    // 注意：不能改成"成功后读回 AirplaneOn()"，RadioKey 由 Windows 的
+    // WlanRadioManager 维护，本程序和 InsydeAirplanemodehid.dll 都不写它，
+    // 读回值永远是旧值，只会把成功误报成失败。
     try { SetAirplaneMode(target ? 1 : 0); }
-    catch (Exception ex) { Log.Write("InsydeAirplanemodehid 调用失败: " + ex.Message); }
+    catch (Exception ex)
+    {
+        Log.Write("InsydeAirplanemodehid 调用失败: " + ex.Message);
+        return !target;
+    }
     Log.Write("飞行模式 -> " + (target ? "开" : "关"));
     return target;
```

> **catch 里是 `return !target;`，不是 `return target;`。**
> 失败意味着状态没变，`!target` 才是"当前实际状态"。

### 4.4 为什么不会引入新问题（已逐项核实）

1. **签名不变**，`bool ToggleAirplane()` → `bool`，两个调用点（`TrayApp.cs:357`、`SettingsPage.xaml.cs:138`）都不用改。

2. **失败时返回值语义更保守**。改动前 DLL 调用失败只写日志、仍然 `return target`（把"意图"当成"结果"上报）。改动后在 `catch` 里 `return !target`——`!target` 恰好等于"原状态"，也就是"没切成功，现在还是原来那样"。

3. **成功路径零改动**。返回值仍是 `target`，与改动前完全一致。**不会出现"把成功误报成失败"**（这正是初版方案的坑）。

4. **不引入注册表写入**。`RadioKey` 在 `HKLM\SYSTEM\CurrentControlSet\Control\RadioManagement\` 下，**普通用户权限写不进去**（需管理员/SYSTEM）。本方案只读不写，绕开权限问题。

5. **`SetWmi` 用 `Try()` 包裹**（原样保留），EC 侧失败被静默容忍，不会因为 EC 不支持而抛异常。

6. **`AirplaneOn()` 自带 try/catch 的前提依然成立但不被本改动依赖**。本改动只在 `catch` 里返回，不新增强制读回，所以即使将来有人动了 `AirplaneOn()` 的 catch，也不会把异常泄漏出 `ToggleAirplane`。

### 4.5 为什么 P0-3（连按两次都是开）不修

要根治"连按两次都是开"，必须让"读"和"写"同源。三条路都行不通或代价过大：

| 思路 | 为什么不做 |
|---|---|
| 写 `RadioKey` 让读回值变对 | **需管理员权限**，普通账户下直接失败；且该键归 Windows Radio Manager 管，硬写会与系统状态打架 |
| 改读源，从 EC 位或 DLL 读真实状态 | 需要先逆向出 `Ex4/GetWmi` 的正确查询码，属扩大改动面，且无实机验证手段 |
| 改成 `bool?` 返回 null 表示失败 | 要动返回类型 + 2 个调用点 + 文案，超出"最小修改" |

**因此 P0-3 保留为已知局限**：若 `SetAirplaneMode` 不写注册表，连按两次会显示"开、开"。实际影响有限——用户看 Windows 通知中心的飞行模式图标即可确认真实状态。

## 五、F4：风扇 D1 —— 改显示源 + 改措辞（P0-1）

### 真实情况（已推翻原报告）

### 那真正的问题是什么

一个**潜伏的数据一致性缺陷**：`D1` 会被 `R12` 斜率消费（`FanCurve.cs:21`），而 `D1` 在 UI 上不可编辑、显示的是固件值，可 `settings.json` 里存的却是**用户自己的值**。

**★经过自检第 13–16 轮补充核实，把这两条链路完整钉死：**

| 环节 | 代码位置 | 用哪个 D1 |
|---|---|---|
| 界面显示 | `FanPage.xaml.cs:68` `double d1 = _defaults is null ? c.D1 : (_defaults.Cpu.D1)` | `_defaults` 非空时用 **WMI 13 读回的固件值**；仅当 `_defaults` 为 null（读固件失败）才用 `c.D1` |
| `_defaults` 来源 | `FanPage.xaml.cs:32` `_defaults = _state.Engine.WithHardware(() => _state.Engine.Fan?.ReadDefaults())` | `FanService.cs:28-37` `ReadDefaults()` 读 `dchu.GetWmiPackage(13)`，`ReadCurve` 用 `DutyToPercent` 反解 |
| 下发 EC | `FanService.cs:96-98` → `PutCurve(b,16,table.Cpu)` → `:103` `b[o]=c.D1`、`:108` `c.R12` | **`settings.json` 里的 `c.D1` 原值** |

`table` 来自 `Settings`（用户保存的方案），与 `_defaults` 完全无关。

实测这台机器：

| 方案 | settings.json 里的 D1 | UI 显示的 D1 | R12 实际用哪个 |
|---|---:|---:|---|
| 安静 | 20 | 固件值（非 20 时即不一致） | **20** |
| 均衡 | 25 | 固件值（恰好相同则看不出差别） | **25** |

**结论：只要 WMI 13 报告的 D1 ≠ settings 里的 D1，用户在界面上看到的和 EC 实际生效的就是两个不同的数。** 而 WMI 13 是固件默认表（`ToWmi14` 从不写 T1/D1 进 WMI 14），所以这个不一致是**可能发生且用户无从察觉**的。

> 注：`PercentToDuty`/`DutyToPercent`（`FanCurve.cs:25-29`）是 255↔100 的有损映射，显示值本身就有 ±1% 的取整误差，但 R12 计算用的是 `c.D1` 原值，不受影响。
