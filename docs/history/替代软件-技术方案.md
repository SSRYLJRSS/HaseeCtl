# Control Center 替代软件：技术方案

日期：2026-10-31。路线 C（完整重写），范围：风扇、性能模式、充电上限、显卡切换、键盘灯、Fn 热键（替换 FnKey）。

## 1. 语言和框架

| 方案 | 安装包 | 安装后 | 界面开着时内存 | 后台常驻内存 | 开发速度 |
|---|---|---|---|---|---|
| **C# .NET 10 + WPF + WPF-UI（推荐）** | 约 70 MB（自包含 zip 实测 69 MB） | 约 170 MB（实测 168 MB） | 约 80 MB 私有内存（空窗口实测 79 MB） | 后台进程用 NativeAOT，预计 10–20 MB | 最快，反编译代码可以直接搬 |
| C# + Avalonia 12（可 NativeAOT） | 约 30–40 MB | 约 60 MB | 约 60–80 MB | 同上 | 快，但控件要自己适配 |
| Rust + Slint/egui | 约 10 MB | 约 15 MB | 约 20–40 MB | 约 5 MB | 慢，协议要从 C# 重新翻译 |

实测数据：本机用 .NET 8 + WPF-UI 4.3.0 建空窗口发布得到。三种方案都满足“安装包 < 100 MB、安装后 < 300 MB”。

选 C# 的理由：原软件就是 C#，FAN.cs、RGBKB.cs、Features.cs 里的命令构造可以几乎原样移植，出错概率最低。内存问题用“两个进程”解决，见第 2 节。

注意：.NET 8 在 2026-11-10 停止支持，所以用 .NET 10（LTS，支持到 2028-11）。本机已有 .NET 10 运行时，还缺 .NET 10 SDK（可装在用户目录，不需要管理员）。

界面库选 WPF-UI 4.3.0（lepoco/wpfui）：Win11 Fluent 风格，支持 Mica 背景、导航页、深浅色主题，文档和示例都比较全。

## 2. 架构

```
HaseeCtl.Core      协议层：IOCTL 直调 AcpiBridge，不依赖 InsydeDCHU.dll
HaseeCtl.Agent     后台进程（NativeAOT，开机自启）：托盘、Fn 热键、OSD、配置自动应用、温度兜底
HaseeCtl.App       设置界面（WPF + WPF-UI），用时打开，关窗即退出
```

- Agent 和 App 通过命名管道通信。
- NativeAOT 不支持 WPF/WinForms，所以 Agent 的托盘图标和 OSD 要直接用 Win32 API 写（工作量可控）。如果这部分不顺利，退回普通 .NET，常驻内存约 30–40 MB。
- 配置保存在 `%APPDATA%\HaseeCtl\profiles.json`，可存多套风扇配置，并按性能模式、插电/电池自动切换。
- Agent 在开机、唤醒、插拔电源、切性能模式后重新应用当前配置。

## 3. 各功能的协议（已从反编译代码确认）

| 功能 | 命令 |
|---|---|
| 风扇读数 | WMI 12（转速、占空比、温度） |
| 风扇曲线 | WMI 14 写曲线，`SetWMI(121,1,6)` 切自定义模式 |
| 性能模式 | `SetWMI(121,25,x)`，App(1,0) 记录 |
| 充电上限 | `SetWMIPackageEx(4,{30,…})` 读，写入 status/start/stop |
| 显卡切换 | `SetWMIPackageEx(4,{21/22,…})`（是否需要重启未确认） |
| 键盘灯 | 本机 WMI13[15]=6，属于 RGB 键盘（不是逐键）。`SetDCHU_Data(103, 4 字节)`：亮度 `0xF4000000+值`，随机模式 `0x70000000`，颜色/区域另有编码；状态存 App 第 2 页 |
| Fn 热键 | 驱动 IOCTL `0x322404` 等待事件，`0x322408` 取键码 |

## 4. Fn 热键链路（逆向结果）

当前链路：AcpiBridge 驱动 → DCHUService（SYSTEM 服务）等待事件 → 把 `Arg001^键码` 写进事件日志 `OutLog` → FnKey 订阅日志后处理。本机日志里能看到 `Arg001^201`（Caps 关闭）。

替换步骤：
1. 第一阶段：保留 DCHUService，Agent 也订阅 `OutLog` 读键码，先把功能做出来。
2. 第二阶段：停用 DCHUService 和 FnKey（一次管理员操作，可随时改回），由 Agent 直接等待驱动事件，并把 App(1,12) 置 0。

安全问题：DCHUService 还监听事件日志 `InLog`，收到 `w_arg255^程序路径` / `w_arg254^…` 会以服务身份启动程序。如果普通用户能写这个日志，就等于本地提权漏洞（未实测）。停用 DCHUService 后这个风险也一起去掉。

## 5. 分阶段计划

| 阶段 | 内容 | 产出 |
|---|---|---|
| 0 | 写入测试：保守曲线写入后恢复；记录本机所有 Fn 键的键码 | 确认权限和持久性，得到键码表 |
| 1 | Core 协议层 + 命令行测试工具 | 每个功能能单独读写 |
| 2 | Agent：托盘、多套风扇配置、自动应用、温度兜底、热键（经 OutLog） | 可以日常使用，和原版并存 |
| 3 | App 界面：风扇曲线编辑器、性能模式、充电、显卡、键盘灯 | 完整设置界面 |
| 4 | 接管：停用 DCHUService/FnKey，Agent 直接收热键，自绘 OSD | 可卸载原版 |
| 5 | Inno Setup 安装包 | 单个安装程序 |

## 6. 风险

- 还没做过任何写入测试。
- 风扇曲线写错可能过热，Agent 会在温度超过阈值时强制切回自动模式。
- 显卡切换和充电上限的写入参数还要逐个核对。
- FnKey 里有大量其他机型的分支（按 ClevoID 区分），只移植本机用得到的部分。
