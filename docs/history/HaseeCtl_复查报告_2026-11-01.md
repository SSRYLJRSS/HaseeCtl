## 零、先说结论（TL;DR）

### 1. 卸载官方 Control Center 后，HaseeCtl 能不能顶上？

**能。核心功能不受影响。** 原因很硬：官方软件是**两层结构**，卸载只掉上面那层应用，底下那层驱动栈**根本不会被删**。

| 层 | 内容 | 卸载 CC 后 | 说明 |
|---|---|---|---|
| 驱动层 | `AcpiBridge.sys` 1.0.0.7（oem22.inf，Insyde）<br>`AcpiBridge1.sys` 1.0.40.0（oem154.inf，CLEVO）<br>`HKKbdFltr.sys` / `HKMouFltr.sys` 2.1.0.6 | **100% 保留** | PnP 驱动包，由 DriverStore 管理，不在 CC 目录里 |
| 服务层 | `CCDCHUService`（AUTO_START，LocalSystem）<br>`HKClipSvc`（AUTO_START） | **100% 保留** | 官方卸载脚本 `sc detele` **拼写错误**，服务从未被删 |
| 应用层 | `C:\Program Files (x86)\ControlCenter` 171 MB<br>UWP `CLEVOCO.FnhotkeysandOSD` 273 MB | **被删** | 这才是卸载真正删掉的东西 |

**HaseeCtl 依赖的是驱动层，而驱动层完全不受卸载影响。** 实测日志 10/10 次连接的都是 `\\?\ACPI#CLV0001#1#{86994c74-...}`，走 oem22.inf / AcpiBridge.sys 1.0.0.7，与 CC 应用层无任何文件依赖。

### 2. 每个选项能不能正常调整？

**能用，但发现 7 个必须修的缺陷**（P0）。其中 3 个会直接让用户"调了没反应或报错结果"：

- **风扇曲线 T1/D1 完全无效**——拖了不会生效，因为它们根本不发给 EC（固件把起转点写死 40°C）
- **飞行模式连按两次永远是"开"**——因为写和读用的不是同一个数据源
- **Fn+触控板快捷键不切换**——只读状态写回，没有真正发切换指令

另有 4 个属于"错得不明显但确实错"：充电上限关闭态不主动下发、`InsydeAirplanemodehid.dll` 缺失时假成功、显卡切换非原子、`ApplyAll` 短路。

### 3. 新旧软件资源占用对比

|---|---:|---:|---|

### 4. 能不能长期稳定运行？

**能。** 三条独立证据：

- **零换页**：整机 `Pages/sec = 0.00`、`Pages Output/sec = 0.00`
- **无泄漏**：30 分钟浸泡，Agent 私有内存 +0.645 MB，但**涨跌比 14:11（有涨有跌，不是单调上升）**，R²=0.68

## 二、卸载官方软件会发生什么（逐组件）

### 2.1 官方卸载程序到底删什么——看它自己的脚本

这是本次复查最关键的一手证据，都来自官方安装目录自身的文件：

**① `C:\Program Files (x86)\ControlCenter\uninstallDCHUService.bat` 全文只有一行：**

```bat
sc detele CCDCHUService
```

`detele` 是 `delete` 的拼写错误。**这个命令从来没生效过**，所以 `CCDCHUService` 从 CC 6.020 发布至今一直残留在每一台机器上。

**② `AppInstall\clean.ini`（卸载时的进程清理名单）——只杀进程，不删服务：**

```
[Program_Name]
DCHUService
fnkey
LaunchFnkey
ComboKeyTray
hkysound
ComboKey
DiskMonitor
PhoneJack
FASer
hkeytray2
hkclipsvc
powerbiosserver
fanspeedsetting
cc
pcc
```

注意它杀了 `DCHUService` 和 `hkclipsvc` 的**进程**，但服务注册（`HKLM\SYSTEM\CurrentControlSet\Services\CCDCHUService`）没有任何删除动作。

**③ `Driver\HKFltrSetup.bat`——支持 `-u` 卸载，但卸载流程从不调用它：**

```bat
call HKFltrInstaller.exe %SETUP_CMD% HKKbdFltr.inf
call HKFltrInstaller.exe %SETUP_CMD% HKMouFltr.inf
call HKClipSvc.exe %SETUP_CMD%
```

这是手动运维工具，`clean.ini` 和 InstallShield 主流程都没有 `call` 它。

**④ UWP 包只装不卸：** `AppInstall\` 下 9 个子目录各有一个 `InstallPackage.bat`，内容都是 `Dism /Online /Add-ProvisionedAppxPackage`。全盘扫描**找不到任何 `Remove-AppxPackage`**。

### 2.2 卸载后残留清单（硬结论）

| 组件 | 卸载后是否残留 | 判定依据 | 影响 |
|---|---|---|---|
| `AcpiBridge.sys` 1.0.0.7 + oem22.inf | **✅ 100% 残留** | PnP 设备 `ACPI\CLV0001\1` 需要它，DriverStore 管理 | **HaseeCtl 的立身之本，必须留** |
| `AcpiBridge1.sys` 1.0.40.0 + oem154.inf | **✅ 100% 残留** | 同上（6.39 MB，15 文件） | 提供 CCDCHUService |
| `CCDCHUService` | **✅ 残留且继续自启** | `sc detele` 拼写错误 + exe 在 DriverStore 不在 CC 目录 | **HaseeCtl 热键的命脉（见 §3）** |
| `HKKbdFltr.sys` / `HKMouFltr.sys` 2.1.0.6 | **⚠️ 高概率残留** | `HKFltrSetup.bat -u` 不自动执行 | **Fn 按键事件的唯一入口** |
| `HKClipSvc` | **⚠️ 残留** | 进程被杀但服务注册还在，`Start=2 Auto` | 每次开机报 Event 7000（找不到文件） |
| UWP `CLEVOCO.FnhotkeysandOSD` 273.29 MB | **⚠️ 残留** | 无 `Remove-AppxPackage` 调用 | 占磁盘；FnKey.exe 57 MB 内存 |
| `C:\Program Files (x86)\ControlCenter` 171.02 MB | **❌ 被删** | InstallShield 正常卸载 | 正常 |

### 2.3 一句话总结

> **卸载 Control Center 删掉的是"控制面板"，不是"控制能力"。**
> 真正的控制能力（`AcpiBridge.sys` + `HKKbdFltr.sys` + `CCDCHUService`）全部在驱动层，卸载碰不到。HaseeCtl 正是站在这一层之上，所以能顶上。

## 三、Fn 热键：最需要说清楚的一件事

这是全篇最容易出错的地方，因为它是"看起来像能工作、实际靠别人的服务"的典型。

### 3.1 真实链路

```
物理按键
  └─> HKKbdFltr.sys（键盘类过滤驱动，UpperFilters 拦截所有按键）
        └─> AcpiBridge.sys（IOCTL 通信）
              ├─ 若 App(1,12)==1 → 路由给 CCDCHUService → 写 EventLog "OutLog" 通道
              └─ 若 App(1,12)==0 → 走驱动通知事件（等待事件）
                    └─> HaseeCtl.HotkeyListener 消费
```

### 3.2 HaseeCtl 有两条通道，会自动切换

`HaseeCtl/src/HaseeCtl.Core/Features/HotkeyListener.cs:54-62`：

```csharp
public bool UseServiceChannel
{
    get
    {
        if (Environment.GetEnvironmentVariable("HASEECTL_FORCE_DRIVER_HOTKEYS") == "1") return false;
        try { return ServiceOwnsEvents && ServiceCheck.IsRunning("CCDCHUService"); }
        catch { return false; }
    }
}
```

- **通道 A（OutLog）**：订阅 Windows 事件日志的 `OutLog` 通道，读 `CCDCHUService` 写入的 `Arg001^键码`
- **通道 B（驱动通知）**：直接 `RegisterWaitEvent` + `ReadNotifyValue`，绕过服务

主循环 `:84-115` 每轮检测通道是否可用，变了就切。

### 3.3 四个场景的实际结果

| 场景 | 热键能否工作 | 证据等级 |
|---|---|---|
| **现状**（CC 已装，CCDCHUService 运行中） | ✅ **工作** | **实测**：日志 10/10 次全是 `热键来源: 服务日志 OutLog` |
| **卸载 CC 后**（服务残留继续跑） | ✅ **仍工作** | **推论（高置信）**：服务 100% 残留自启，`ServiceCheck.IsRunning` 仍为 true → 继续走已验证的通道 A |
| 手动 `sc delete CCDCHUService` | ⚠️ **未知** | 通道 B 从未收到过真实键码。但"打开设备+注册通知"三步已实测成功 |
| 手动跑 `HKFltrSetup.bat -u` | ❌ **彻底失效** | `UpperFilters` 被清空 → 两个通道都没有输入源 |

### 3.4 关于通道 B 的实测（诚实标注边界）

我实际跑了探针 `HaseeCtl.Probe.exe --driverkeys 8`：

```
驱动热键通道已注册，等待 8 秒…（请按 Fn 组合键）
共收到 0 个键码
```

**这个"0 个键码"不是 bug**，原因是当前 `App(1,12) == 1`（基线 dump 的 `0x10C` 字节就是 1），意味着固件把事件路由给了服务，**不发给驱动通知通道**。探针在这个模式下必然收 0。

**但这一跑证明了一件重要的事**：`OpenEventHandle` → `CreateEventW` → `RegisterWaitEvent` 三步**全部成功**（任何一步失败都会抛异常）。所以通道 B 的"基础设施"是通的，未验证的只剩"能否真正收到键码"。

### 3.5 建议

**卸载 CC 后不要动 `CCDCHUService`。** 它是热键的命脉，且它不是 CC 的一部分（属 oem154 驱动包）。让这个看起来"多余"的服务继续跑，热键就是 100% 可靠的。

如果你出于洁癖一定要删它，就要接受"热键走未验证通道"的风险——**而这个风险目前无法在不打扰你使用的前提下消除**。

**关于 P0-1 的详解（必须看懂）**：

`HaseeCtl/src/HaseeCtl.Core/Features/FanCurve.cs:7-8` 的注释自己写得很清楚：

> *Only points 2 and 3 plus the three slopes are sent to the EC (WMI 14)*

实际发给 EC 的只有：

```csharp
b[o]   = c.T2;                    // 温度点 2
b[o+1] = PercentToDuty(c.D2);     // 占空比 2
b[o+2] = c.T3;                    // 温度点 3
b[o+3] = PercentToDuty(c.D3);     // 占空比 3
b[o+4] = 40;  // ← 硬编码！起转温度固定 40°C
b[o+5] = 80;  // ← 硬编码！起转占空比固定
```

而 `FanService.cs:105-113` 写死了 `40` 和 `80`。所以：

- **改 T1 → 什么都不发生**（因为起转点写死 40°C）
- **改 D1 → 只改变 T1→T2 这段的斜率**，但因为 T1 恒等于 40，实际改的是"40°C 到 T2 之间爬升多快"，**改不了"40°C 时风扇转多少"**
- 你的 settings.json 里存了 `d1=25`，但实际下发的是 `80`——**差了 3.2 倍**

**建议**：把 T1/D1 从 UI 上删掉。留着它俩只会让用户以为能调，实际调不了，属于"欺骗性 UI"。

### 7.3 句柄锯齿：已查清，不是泄漏

这是本次复查中最曲折的一节。**结论：不是泄漏，但确实异常，当前无害。**

**观测到的现象**：

- 09:30:28 → 09:49:07：句柄从 687 **单调升到 913**（+226，19 分钟）
- 09:49:38：**骤降到 469**（−444）
- 之后重新爬升：477 → 483 → ... → 811（10:18）
- 速率恒定：**+6 个 / 30 秒**（+12 / 分钟，+720 / 小时）

**根因定位（三条独立证据）**：

**证据 1：句柄类型差分（perf-meter 用 `NtQuerySystemInformation` 做的）**

每 30 秒 **+6 Thread 句柄 + 12 Event 对象**，其余 14 类（含 File）**全部 delta = 0**。

→ **设备句柄根本没堆积**。这直接排除了"每次调用开一次设备句柄"的假设（`CreateFileW` 产生的必然是 File 类型）。

**证据 2：句柄/线程比值异常**

| 进程 | 活线程 | Thread 句柄 | 比值 |
|---|---:|---:|---:|
| HaseeCtl.Agent | 15 | **105** | **7.0** |
| HaseeCtl.App | 24 | 40 | 1.67 |

Agent 稳态下背着约 **90 个已退出 worker 的 Thread 对象**（`Thread` 对象仍在堆上被句柄引用）。

**证据 3：源代码根因**

`HaseeCtl/src/HaseeCtl.Agent/TrayApp.cs:101-120`：

```csharp
private void RunMaintenance()
{
    if (Interlocked.Exchange(ref _maintenanceBusy, 1) == 1) return;
    Task.Run(() =>
    {
        try { ... }
        catch { ... }
        finally { Volatile.Write(ref _maintenanceBusy, 0); }
    });   // ← Task 被丢弃，不 await、不观察
}
```

每 30 秒裸 `Task.Run`，Task 被丢弃。线程池按需拉起 worker，每个 worker = 1 Thread 句柄 + 2 Event 对象，**正好对上 +6/+12 的比例**（6 个 worker）。

全仓库 `Task.Run` 只有 2 处（`:85` 用户操作、`:104` 每 30 秒），与观测到的 30 秒周期严格对应。

**证据 4：回收机制——是 GC 不是线程池 trim（我最初判断错了，这里修正）**

我一开始以为是"线程池 worker 空闲超时（`ThreadTimeoutMs`）后退出"。**这个假设被数据否掉了**，两个理由：

**否证 A**：`_verify/trim_cpu_corr.csv` 39 个采样点，10:07:23→10:18:11 连续 **11 分钟句柄从 679 单调涨到 811，一次回落都没有**，期间 CPU 在 0.0%~33.8% 剧烈波动。如果是 `ThreadTimeoutMs`（十几秒级）在检查，不可能 11 分钟不触发。

**否证 B**：09:49:38 那次回收的完整字段对比——

| 指标 | 09:49:07 | 09:49:38 | 变化 |
|---|---:|---:|---:|
| 句柄 | 913 | **469** | **−444** |
| 工作集 | 5.27 MB | **14.47 MB** | **+9.20 MB** |
| 私有工作集 | 2.45 MB | **6.31 MB** | +3.86 MB |
| CPU 累计 | 1.047 s | **1.062 s** | +15 ms（该轮 CPU% = 0.05%，其他 12 轮均为 0） |
| 分页池 | 17,352 KB | **18,032 KB** | +680 KB |

**句柄掉了 444 个，工作集反而暴涨 9.2 MB，CPU 出现唯一一次尖峰，分页池同步增长。**

这四个信号同时出现，是 **GC 在遍历堆**的典型指纹（遍历要逐页触碰对象头，把冷页拉进工作集）。线程池 trim 是轻量操作，不会造成这种内存行为。

**正确机制**：

> Thread 对象是 GC 管理的对象。池 worker 退出后 `Thread` 对象仍留在堆上；只有 **GC 判定其死亡并执行 finalizer** 时，OS Thread 句柄与配对 Event 才释放。GC 要积累到阈值才触发，所以表现为"长时间线性累积 → 一次性批量释放 → 重新累积"。

**为什么不构成危害**：

- **有界**：30 分钟长周期观测（10:11:45→10:26:45）句柄 733→795→855→**915**，与上午那次峰值 **913 几乎完全一致**。两次独立周期都收敛到 910 附近，说明回收点稳定，不是无限增长
- **不转化**：同一组 30 分钟数据里，**私有内存 4 次采样全部是 17.61 MB，一字未变**，而句柄涨了 182 个。这直接证明残留 Thread 对象对应的线程栈页**从未被触及**（未提交），完全不占物理内存。这是比任何单点证据都硬的挡板
- **量级小**：+720/小时，即使 24 小时不回收也只有 17,280 个，占系统总句柄（实测 182,861）的 9.4%

**建议的修法**（不是必须，是优化）：

```csharp
// 方案一：用 System.Threading.Timer（专用线程，不消耗线程池）
new Timer(_ => RunMaintenance(), null, TimeSpan.Zero, TimeSpan.FromSeconds(30));

// 方案二：async 循环，复用同一个 worker
private async Task MaintenanceLoopAsync(CancellationToken ct)
{
    while (!ct.IsCancellationRequested)
    {
        RunMaintenance();
        await Task.Delay(30000, ct);
    }
}
```
